## 1. 문서 목적과 범위

### 포함

- 허브, 공통 파일 처리 런타임, 형식별 변환기와 편집기의 책임
- 브라우저 내부 데이터 흐름과 저장 경계
- 파일·메모리·Canvas 안전 한도와 실패 정책
- Sites 정적 번들 및 Worker 경계
- 테스트, CI와 Git Markdown -> Notion 미러 절차

### 제외

- 실제 운영 URL의 가용성·성능·사용자 트래픽
- 모든 PDF/PPTX 문서의 렌더링 호환성
- 계정, 서버 저장소, 동기화, 결제, 서버 변환 큐
- 문서에 없는 미래 기능을 구현된 것처럼 평가하는 주장

## 2. 문제 맥락과 제약

Tool Page가 줄이려는 비용은 단순 파일 작업을 위해 여러 서비스로 이동하고 원본을 업로드하는 과정입니다. 현재 범위에서 높은 ROI는 별도 백엔드나 계정 시스템이 아니라, 브라우저가 이미 제공하는 파일·미디어 API를 일관된 UX로 묶는 것입니다.

주요 제약은 다음과 같습니다.

- 정적 호스팅에서 동작해야 하며 서버 API를 전제로 하지 않습니다.
- 외부 CDN 없이 저장소에 고정한 라이브러리와 글꼴로 실행합니다.
- 브라우저 메모리와 Canvas 크기에는 명확한 상한이 있습니다.
- 문서 형식은 브라우저 라이브러리가 해석할 수 있는 범위만 지원합니다.
- 실패 시 일부 결과를 조용히 누락하기보다 중단하고 원인을 표시합니다.

## 3. 사용자와 핵심 흐름

| 사용자 | 목표 | 핵심 흐름 |
| --- | --- | --- |
| 반복적인 파일 정리가 필요한 사용자 | 빠르게 도구를 찾아 여러 파일을 같은 규칙으로 처리 | 검색/필터 -> 파일 선택 -> 정렬/설정 -> 변환 -> 다운로드 |
| 원본 업로드를 피하려는 사용자 | 로컬 브라우저에서 작업 완료 | 파일 읽기 -> 브라우저 변환 -> Blob 생성 -> 로컬 다운로드 |
| 문서 페이지를 이미지로 나누려는 사용자 | 페이지/슬라이드를 순서대로 ZIP 저장 | 문서 검증 -> 페이지 렌더 -> 고유 파일명 -> ZIP 출력 |

```text
[File / FileList]
  -> 형식·개수·바이트 예산 검증
  -> 미리보기 URL과 작업 상태 생성
  -> 형식별 파서 / Canvas / Web Audio / Worker
  -> Blob 또는 문서 객체
  -> 고유 파일명 부여
  -> Object URL 기반 다운로드
  -> 임시 URL 정리
```

## 5. 시스템 아키텍처

```text
[index.html + scripts/home.js]
  -> 도구 검색 / 카테고리 / 최근 사용 진입
  -> [tools/*.html]
       -> [app.js 공통 런타임]
            - 파일 큐와 예산 검증
            - 정렬·재배치·설정 저장
            - 작업 토큰과 취소
            - 미리보기·다운로드·파일명 충돌 방지
       -> [scripts/converter-*.js]
            - 이미지 / GIF / PDF / PPTX 변환
       -> [scripts/editor-*.js]
            - 단일·일괄 이미지 / MP3 편집
       -> [assets/vendor/*]
            - PDF.js, PptxGenJS, JSZip, jsPDF, gif.js, lamejs, UTIF

[scripts/build-sites.mjs]
  -> dist/client 정적 자산
  -> dist/server Worker
       - 보안 헤더
       - GET/HEAD 제한
       - 확장자 없는 도구 경로 보정
```

## 6. 불변 규칙과 안전 한도

1. 현재 작업이 취소되거나 새 작업으로 교체되면 이전 작업 토큰은 결과를 반영하지 않습니다.
2. 같은 기본 이름의 결과는 자동으로 고유 이름을 받아 기존 파일과 충돌하지 않습니다.
3. 요청한 출력 MIME을 브라우저가 생성하지 못하면 다른 형식에 잘못된 확장자를 붙이지 않고 실패합니다.
4. 다중 페이지 TIFF와 미지원 PPTX 요소는 조용히 일부만 출력하지 않고 중단합니다.
5. 미리보기 Object URL은 파일 제거·상태 교체·페이지 종료 시 정리합니다.
6. 입력 개수·바이트·픽셀·페이지·슬라이드 한도를 넘으면 변환을 시작하지 않습니다.

| 경계 | 현재 한도 |
| --- | --- |
| 공통 파일 입력 | 최대 100개, 파일당 120MB, 전체 250MB |
| 이미지 형식 변환 | 한 변 16,384px, 8천만 픽셀 |
| PDF 페이지 이미지 | 120페이지, Canvas 한 변 16,384px, 8천만 픽셀 |
| PPTX 이미지 변환 | 100슬라이드 |
| 단일 이미지 편집 | 60MB, 2,400만 픽셀 |
| 일괄 이미지 편집 | 50장, 전체 250MB, 한 변 8,192px, 전체 출력 1억 5천만 픽셀 |
| MP3 편집 | 150MB |

## 7. 핵심 기술 의사결정

### 결정 1. 서버 변환 대신 브라우저 로컬 처리

- **상황**: 단순 파일 작업에 업로드·대기·다운로드와 서버 운영이 추가됩니다.
- **선택**: File API, Canvas, Web Audio API, Worker와 로컬 라이브러리로 처리합니다.
- **근거**: 현재 범위의 형식은 브라우저 안에서 처리 가능하며 계정·저장·백엔드 운영 비용을 제거할 수 있습니다.
- **비용**: 기기 메모리·브라우저 구현 차이·문서 형식 호환성의 영향을 직접 받습니다.
- **재검토 조건**: 로컬에서 감당할 수 없는 대용량 처리나 서버에서만 가능한 고정밀 렌더링이 핵심 요구가 될 때입니다.

### 결정 2. 공통 런타임 + 형식별 얇은 모듈

- **상황**: 드롭존, 파일 큐, 설정, 취소, 결과 다운로드가 여러 도구에서 반복됩니다.
- **선택**: `app.js`가 공통 상태와 UI를 소유하고 각 변환 모듈이 `ToolPage.registerTool`로 형식 책임을 등록합니다.
- **근거**: 동일 UX를 한곳에서 수정하면서 형식별 장애 범위를 분리할 수 있습니다.
- **비용**: `app.js`가 큰 중심 모듈이므로 추가 기능이 계속 들어가면 책임 분리가 다시 필요합니다.

### 결정 3. 단일 이미지와 일괄 편집을 분리

- **상황**: 단일 편집은 포인터 좌표, 크롭, 히스토리가 중심이고 일괄 편집은 다중 파일 예산과 공통 출력 크기가 중심입니다.
- **선택**: `editor-image.js`와 `editor-image-batch.js`를 별도 상태 머신으로 유지하고 필요한 검증 helper만 공유합니다.
- **근거**: 한 모듈에 두 UX를 섞을 때 생기는 조건 분기와 회귀 범위를 줄입니다.
- **비용**: 공통 출력·검증 규칙이 바뀌면 두 모듈을 함께 점검해야 합니다.

### 결정 4. 라이브러리를 저장소에 고정

- **상황**: CDN 장애, 버전 변동, 실행 중 제3자 네트워크 연결을 피해야 합니다.
- **선택**: `assets/vendor/`에 필요한 브라우저 번들을 포함하고 버전과 SHA-256을 기록합니다.
- **근거**: 배포 산출물과 로컬 검증이 같은 런타임 파일을 사용합니다.
- **비용**: 취약점과 새 버전 검토를 저장소가 직접 책임져야 합니다.

### 결정 5. Git Markdown을 문서 원본으로 유지

- **상황**: Git 문서와 Notion을 둘 다 직접 수정하면 내용이 갈라집니다.
- **선택**: `docs/Project_Intro.md`와 `docs/Project_Detail.md`만 편집하고, Notion은 전용 페이지의 replace-only 미러로 취급합니다.
- **근거**: 코드 변경과 문서 근거를 같은 리뷰·커밋 경계로 추적할 수 있습니다.
- **비용**: Notion 미러 페이지의 수동 본문 편집은 다음 발행에서 대체됩니다.

## 8. 외부 연동과 실패 경계

런타임 변환 자체에는 서버 API가 없습니다. 외부 경계는 정적 호스팅과 문서 발행입니다.

| 연동 대상 | 목적 | 인증/비밀값 | 실패 처리 | 이번 확인 |
| --- | --- | --- | --- | --- |
| Sites 정적 자산 환경 | 클라이언트·Worker 배포 | 호스팅 프로젝트 설정 | 빌드/배포 단계 실패 | 로컬 번들만 검증 |
| GitHub Actions | 품질 및 문서 검증 | 기본 읽기 권한 | 실패한 job으로 push 상태 표시 | 워크플로 파일 확인, 새 원격 run은 push 후 확인 대상 |
| Notion API | 전용 미러 페이지 본문 교체 | `NOTION_TOKEN`, `NOTION_PAGE_IDS_JSON` | 모든 페이지 preflight 후 실패 시 중단 | 연결·실제 발행 미수행 |

## 9. 데이터 보호와 보안

| 경계 | 정책 | 저장소 근거 |
| --- | --- | --- |
| 파일 처리 | 원본을 서버 API로 전송하지 않고 브라우저에서 처리 | 변환·편집 스크립트, 서버 API 부재 |
| 네트워크 | 런타임 라이브러리·글꼴을 로컬 자산으로 제공 | `assets/vendor/`, `assets/fonts/` |
| Worker 메서드 | GET과 HEAD만 허용, 상태 변경 메서드는 405 | `scripts/build-sites.mjs`, 배포 테스트 |
| 브라우저 권한 | camera, geolocation, microphone 비활성화 | Worker `Permissions-Policy` |
| 임베딩·MIME | `X-Frame-Options: DENY`, `nosniff`, CSP 적용 | Worker 보안 헤더 |
| 문서 비밀값 | 페이지 ID와 토큰을 저장소에 쓰지 않고 GitHub Environment secret 사용 | 문서 워크플로와 설정 schema |

구조상 서버 업로드 경로가 없다는 사실은 확인했지만, 브라우저 확장 프로그램·사용자 기기·호스팅 사업자 전체를 감사했다는 의미는 아닙니다.

## 11. 배포·운영·복구

```text
[main 또는 PR 변경]
  -> Quality: npm ci -> 정적 검증 -> 배포 테스트 -> Chromium/WebKit E2E -> audit
  -> Sites 빌드: dist/client + dist/server
  -> 호스팅 배포는 별도 플랫폼 경계

[문서 변경]
  -> 문서 validator
  -> Notion 렌더 dry-run
  -> 수동 workflow_dispatch + operation=publish + PUBLISH
  -> notion-production 환경
  -> 전용 Notion 페이지 replace_content
```

- **배포 조건**: 품질 워크플로는 PR과 `main` push에서 실행하도록 구성되어 있습니다.
- **관찰 항목**: CI 실패, 정적 자산 404, 보안 헤더, 브라우저 런타임 오류, 형식별 변환 실패를 확인해야 합니다.
- **복구**: 정적 자산은 이전 정상 커밋으로 되돌려 재빌드할 수 있습니다. 실제 플랫폼 rollback 절차는 이번 저장소 검증에 포함되지 않았습니다.
- **문서 복구**: Git의 정상 문서 커밋을 다시 수동 발행하면 전용 Notion 미러가 동일 revision으로 수렴합니다.
- **문서 발행 경계**: 일반 push는 `publicationMode: manual`이므로 Notion 본문을 자동 변경하지 않습니다.

## 12. 한계, 기술 부채, 다음 단계

| 우선순위 | 항목 | 영향 | 다음 행동 |
| --- | --- | --- | --- |
| P1 | 실제 형식 fixture 범위가 제한적 | 복잡 PDF/PPTX·오디오·TIFF에서 회귀 발견이 늦을 수 있음 | 공개 가능한 대표 fixture와 예상 결과 검증 추가 |
| P1 | 운영 배포와 실제 기기 검증이 문서 근거에 없음 | 로컬 통과가 운영 가용성으로 오해될 수 있음 | 배포 후 smoke URL·헤더·주요 다운로드 경로를 기록 |
| P2 | 중심 모듈 `app.js`의 책임이 큼 | 공통 UX 변경의 디버깅 경로가 길어질 수 있음 | 다음 공통 기능 추가 시 파일 예산·큐·다운로드 책임 분리 검토 |
| P2 | Firefox·저메모리 모바일 미검증 | 브라우저별 Canvas/Web Audio 차이를 늦게 발견 | 최소 Firefox E2E와 실제 모바일 smoke matrix 추가 |
| P2 | 저장소 내 vendor 업데이트가 수동 | 보안·호환성 업데이트가 늦어질 수 있음 | 정기 버전·해시·라이선스·audit 검토 절차 문서화 |

지금 해야 하는 단 하나는 대표 실파일 fixture 묶음을 만들고, 성공뿐 아니라 의도된 실패 메시지까지 회귀 테스트로 고정하는 것입니다. 서버 변환이나 사용자 계정은 이 검증 기반이 안정된 뒤에만 재평가합니다.
